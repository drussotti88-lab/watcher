Integration spec · Sentinel v0.2

Order Tracking Subsystem

Adding email-derived order tracking and release-day cash forecasting to Sentinel, so the system that tells you to buy also tells you what buying cost you and when the money actually leaves.

Target vault_sentinel @ 0.1.0 Source PokeTrack (Python, working, tested) New module src/orders/

01

Thesis

Sentinel's lifecycle ends at "it's in stock, go buy it." Nothing downstream of the buy decision is tracked. The system fires alerts all month and has no idea what those alerts cost.

// today
watch → alert → [ nothing ]

// with this subsystem
watch → alert → buy → order mail → owed → charged → own
                 └─ Sentinel already does this half ─┘

The new half is entirely email-derived. A retailer's order confirmation is a fact you already receive; nobody has to remember to log anything. What comes out the other end is a single question answered: how much do I need available on the 26th, and which orders make it up.

This matters more than it sounds for pre-orders specifically. Pokémon Center authorizes at order time and charges at ship — so a month of pre-ordering produces no card activity at all, then several hundred dollars on one release day. That's the number the system should be shouting about, and it currently can't see it.

02

Where it attaches

This is not an adapter. The RetailerAdapter contract is resolve(url) + check(watch) → CheckResult — one product, one stock state, polled on a URL. An inbox has no product id and returns N orders per poll. Forcing it into that contract would corrupt the adapter model for every future retailer.

Precedent already in the codebase

SiteMonitor is a non-adapter watcher: its own cadence, its own loop, posts to Discord directly, isolated in index.ts so a failure can't take the engine down. The mail scanner is the same species. Follow it exactly.

src/index.ts modify

  const siteMonitor = new SiteMonitor();
  void siteMonitor.start().catch((err) => { /* ... */ });

  // Order tracker: scans mail for order/shipping/cancellation notices and
  // posts release-day cash warnings. Isolated like SiteMonitor — a mail
  // outage must never stop stock polling.
  const orderTracker = new OrderTracker();
  void orderTracker.start().catch((err) => {
    logger.error('order tracker crashed', {
      error: err instanceof Error ? err : new Error(String(err)),
    });
  });

  const shutdown = (signal: string) => {
    engine.stop();
    siteMonitor.stop();
    orderTracker.stop();
    /* ... */
  };

Four independent loops instead of three. Nothing in Engine, stateMachine, or any adapter changes.

Naming

orders is generic for a Postgres instance you may later share with DNA Card Vault. If co-location is likely, prefix the whole set (ord_orders, etc.) now rather than migrating later. Everything else is already namespaced enough.

05

The scanner loop

OrderTracker runs two independent timers on one loop — they have nothing to do with each other and shouldn't share a cadence.

TimerDefaultDoes
Mail scan900sFetch new mail, match rules, upsert orders, alert on transitions
Cash digestDailyRecompute allocation, post a warning for anything landing inside the horizon

Fifteen minutes, not forty-five seconds. An order email is not time-critical the way a restock is — the thing it's warning you about is days away.

O-1

Fetch headers before bodies. IMAP-search each enabled account for SINCE <since_days> + FROM <term>, once per sender term across all enabled rules, then union the UIDs. Only fetch full bodies for UIDs whose Message-ID isn't already in order_messages.

O-2

Cap the batch. Process at most 50 new messages per tick and carry the rest to the next one. See §11 — the box is 256MB.

O-3

Store the flattened text, never raw HTML, capped at 200KB. Prefer whichever of the plain and HTML parts carries more content — marketing mail routinely ships a near-empty plain part.

O-4

Re-apply without re-fetching. Editing a rule must rebuild orders from order_messages alone, no IMAP round-trip. This is what makes rules iterable; the existing implementation treats it as non-negotiable and so should this one.

O-5

A mail failure is logged and skipped, never thrown past the loop. Per-account last_status carries the reason so /status can surface it, exactly like adapter health.

06

Ported logic

Three files, ~600 lines of Python becoming TypeScript. The semantics below are what make it predictable — port them precisely; the reference implementation's tests exist to prove you did.

rules.ts

O-6

Every non-empty condition must pass; blank conditions are ignored. Within one condition, comma-separated terms are OR'd. subject_excludes inverts — any hit fails the rule. Matching is case-insensitive substring unless use_regex, in which case an invalid pattern fails closed rather than throwing.

O-7

Sender matching runs against display name and address concatenated. Rules evaluate in ascending priority then created_at; first match wins. A rule with zero conditions matches nothing — never everything.

parser.ts

O-8

Total extraction is priority-ordered: labelled totals (order total, grand total, total charged) first, then bare total, then a trailing amount. Taking the first dollar figure returns the subtotal and is wrong.

O-9

Line items try several layouts in turn. Lines containing subtotal, shipping, tax, discount are never products. Return zero items rather than fabricated ones.

O-10

No order number, no total, or items summing above the total → the message goes to needs_review with a plain-language note. Never silent, never thrown.

ledger.ts

The substance. Runs over every order that is not charged with status preorder or open, allocating money to dates — per line item where possible, so an order spanning two release months splits across both.

for (const order of unchargedOpenOrders) {
  // Explicit beats inferred, in this order
  if (order.charge_date)            allocate(order.charge_date, order.total)
  else if (order.release_date)      allocate(order.release_date, order.total)
  else if (timing === 'at_order')   allocate(order.order_date, order.total)
  else {
    let matched = 0
    for (const item of order.items) {
      const rel = bestReleaseMatch(item.name, order.retailer_name)
      if (rel) { allocate(rel.release_date, item.line_total); matched += item.line_total }
    }
    const leftover = order.total - matched   // tax, shipping, unmatched

    if (matched > 0 && leftover > 0) allocate(latestMatchedDate, leftover)
    else if (matched === 0) {
      const fb = bestReleaseMatch(allItemNames, order.retailer_name)
      fb ? allocate(fb.release_date, order.total)
         : allocate(UNSCHEDULED, order.total)
    }
  }
}
O-11

bestReleaseMatch returns the release whose longest matching term appears — most specific wins. A release with retailer_name set matches only that retailer.

O-12

Allocation is computed on read, never stored. Changing a release date moves the money immediately, with no rescan.

O-13

Undatable money goes to an explicit unscheduled bucket, surfaced in Discord and the dashboard. Never silently dropped, never folded into a real date.

O-14

Hand edits win permanently. Editing any order field appends it to locked. No scan, upsert or rebuild may overwrite a locked field. Orders with notes, and hand-created orders, survive a rebuild untouched.

07

Alert state machine

Your stock rule is "alert on transitions, not states." Orders follow the identical philosophy in src/orders/orderState.ts — a pure decide() with an injectable now, exactly like core/stateMachine.ts.

TransitionAlertWhy it's worth a ping
— → order recorded🧾 New orderConfirms the tracker saw what you bought
preorder/open → shipped💳 ChargedMoney just left; the forecast changed
any → cancelled↩️ CancelledMoney you thought you owed, you don't
charge date enters horizon⏳ Due soonThe point of the whole subsystem
parse failed⚠️ to #opsSame channel adapter degradation already uses
O-15

Dedup via orders.last_alerted against a cooldown, mirroring watches.last_alerted. The due-soon warning fires once per order per horizon crossing — not daily until the date passes. A daily digest that repeats itself gets muted, and then the one that mattered gets muted with it.

O-16

The digest is a single embed for a date, not one per order. "$346.84 clears Friday across 3 orders" with the orders as fields.

08

Discord surface

One new channel, #orders, alongside the retailer channels — configured by webhook URL the way opsChannelId already is. Order alerts optionally cross-post to the retailer's own channel when order_rules.retailer_id is set.

Slash commands src/bot/commands.ts

Kebab-case, matching the existing set. Each delegates to src/service/orderActions.ts so the control API shares the logic — the same split watchActions.ts already enforces.

CommandEffect
/cash-due [days]What's owed, by date, within the horizon. The headline command
/list-orders [status] [retailer]Open orders with charged/owed state
/add-release product date [match] [price] [tcg_sku]Manual release-date entry
/list-releasesCalendar with money committed to each

Capability neither system had alone

order_items.tcg_sku + your existing price_cache and MarketPriceService means the due-soon embed can carry a cost-basis line: "$346.84 clears Friday — 3× Mega Evolution ETB at $59.99 against a $71 market median." Sentinel already computes that number for restock alerts; here it prices what you actually committed to. Cheap to add once tcg_sku is populated, and it's the strongest argument for this living in Sentinel rather than anywhere else.

Secrets

Mail passwords follow mail_accounts.secret_ref → environment, not the DB:

fly secrets set \
  MAIL_PRIMARY_GMAIL=xxxxxxxxxxxxxxxx \
  MAIL_SECONDARY_OUTLOOK=xxxxxxxxxxxxxxxx \
  ORDERS_WEBHOOK_URL=https://discord.com/api/webhooks/...

A row stores secret_ref = 'MAIL_PRIMARY_GMAIL' and the scanner reads process.env[row.secret_ref]. This is deliberately stricter than retailers.config — a mail password reaches far more than a RedSky key does, and it keeps the DB free of anything worth stealing.

O-17

App passwords only, never a primary account password. Providers reject the latter for IMAP anyway, and an app password can be revoked without touching the account.

O-18

If secret_ref resolves to nothing, the account is skipped with a loud #ops warning. It must not fall back to any other credential.

10

Dashboard

The Next.js dashboard already has auth, WatchTable, AddItemForm, and a server-side-only CONTROL_API_URL pattern. Orders slot in as a second route reusing all of it — no new auth surface, no new token, no CORS.

  • /orders — the cash timeline as the hero, orders table beneath it
  • /releases — release-date CRUD, showing money committed to each
  • /orders/[id] — edit any field; edited fields show as locked
  • /review — the needs_review queue with the parse note

New API routes in src/api/server.ts, same bearer-token gate and same shape as the existing /api/watches handlers: GET/POST /api/orders, PATCH/DELETE /api/orders/:id, GET/POST /api/releases, GET /api/cash-due.

None of PokeTrack's own UI comes across — roughly 70KB of Python-rendered HTML and hand-built SVG charts. It exists because the standalone app had nowhere else to draw. This dashboard supersedes all of it.

11

Constraints

Memory · the real one

The Fly machine starts at 256MB. A first scan over 540 days across multiple accounts will OOM if it fetches everything into memory — which is exactly what the local Python version does, because a desktop has room to be sloppy. O-1 and O-2 are not optimizations, they're requirements: headers first, bodies only for unseen messages, 50 per tick. If it still OOMs, fly scale memory 512 before loosening the batch.

Blast radius

The worker already holds a Discord bot token, a Supabase service key, and eBay credentials. Adding mail app passwords means one compromised host reaches your inbox too. Still better than a lightly-obfuscated SQLite file on a Windows desktop — but it's a conscious widening, and app passwords (O-17) are what keep it revocable.

One thing that gets easier

SiteMonitor's own docstring notes that Pokémon Center 403s datacenter IPs, so server-side watching needs a residential proxy or the browser extension. IMAP has no such problem. Mail servers don't care that you're connecting from Fly. This subsystem works properly on the host where your hardest adapter is compromised.

Smaller ones

  • Retailers change email templates constantly. The needs_review queue is the designed response, not a bug — expect to use it after the first real scan.
  • Order emails carry no release date. That data is manual, permanently. Don't design as though it will arrive.
  • Partial shipments splitting one order across dates are out of scope for v1.
  • orders.locked as text[] assumes Postgres arrays; if the Supabase client round-trips them awkwardly, jsonb matches retailers.config precedent better.
12

Build order

Each phase ships something usable. Resist starting with IMAP — it's the most visible piece and the least important to get right first.

P-1

Schema + ledger + manual entry. Tables, ledger.ts, /add-release, /cash-due, and hand-created orders via orderActions. No email anywhere. This answers the actual question and de-risks the only part that's subtle.

P-2

Rules + parser, offline. Ported logic plus its test suite, driven from pasted message text. Fully testable with no IMAP and no network.

P-3

The loop. mailbox.ts, OrderTracker, wiring into index.ts, needs_review, /scan-mail, /reapply-rules.

P-4

Alerts. orderState.ts, orderEmbeds.ts, the #orders channel, due-soon warnings.

P-5

Dashboard + market enrichment. The four routes, then tcg_sku on line items and the cost-basis line in the digest.

13

Acceptance

Ported from the reference implementation's passing suite. Run under node --test --import tsx like the existing *.test.ts files. Real numbers — an implementation that reproduces them is correct.

Rules

  • "Your pre-order is confirmed" from orders@pokemoncenter.com → pre-order rule, not the order rule
  • "Your order has shipped" from shipping@pokemoncenter.com → shipping rule
  • "New arrivals at Pokémon Center" from news@pokemoncenter.com → no match
  • A Target order containing only bath towels → no match (the body_contains guard)

Parser

  • Subtotal 124.97, tax 10.31, order total 135.28 → extracted total is 135.28
  • Same message → exactly 2 items; none named "Subtotal", "Estimated Tax" or "Shipping"
  • Qty 2 × $49.99 → line total 99.98
  • A shipping notice for an existing order updates it to shipped with tracking; order count unchanged

Ledger

Two uncharged pre-orders plus a Target order, against mega evolution → 2026-09-26 and destined rivals → 2026-10-17:

AssertionExpected
Owed on 2026-09-26 (two retailers, one release)346.84
Owed on 2026-10-17175.30
Unscheduled0.00
Total still owed522.14
Total already charged309.85

346.84 spans two retailers releasing the same product on the same day — the timeline is organised by date, not by order. That's the case a per-order view gets wrong.

  • Move destined rivals to 2026-11-07 → the 10-17 bucket vanishes, an 11-07 bucket appears, with no rescan
  • A cancelled order contributes zero to both owed and charged
  • Hand-edit a total to 999.00, then rebuild → still 999.00, notes intact
  • Rebuild twice → order count unchanged both times
Reference implementation: PokeTrack — Python, standard library only, full passing suite. Logic to port lives in rules.py, parser.py and money.py. Its UI layer is not carried over.
