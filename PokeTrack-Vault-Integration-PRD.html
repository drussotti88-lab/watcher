Product requirements

Order & Release-Day Cash Tracking

Folding PokeTrack — a working standalone app — into the DNA card vault, so a pre-order is tracked as inventory you don't have yet and the vault can tell you what cash you need ready on each release date.

Status draft for implementation Reference impl PokeTrack, Python, working Target stack to be determined by implementer

01

Why this exists

The card vault knows what you own. It does not know what you have committed to. For someone buying sealed product across multiple retailers, the money that matters is usually money that hasn't left the account yet — pre-orders that will all charge on the same release day, from stores that authorize at order time and charge at ship.

The problem being solved is a cash-timing problem, not an inventory problem: how much do I need available on September 26, and which orders make up that number.

A standalone version of this exists and works — it reads multiple inboxes over IMAP, matches order mail against user-defined rules, extracts orders and line items, and renders the cash timeline. This document specifies folding that capability into the vault rather than running two apps. The existing implementation is a reference for logic and test expectations, not code to copy.

02

The core idea

An order is incoming inventory. A pre-order is something you own on paper but not in hand. On delivery it graduates into the vault proper. That gives one continuous timeline instead of two disconnected apps:

ordered  →  pre-order  →  shipped  →  delivered  →  vault item
   ↑                          ↑                            ↑
 money owed            money charged              inventory owned

This is the integration point that makes the merge worth doing. If orders just sit in a side table with no relationship to vault items, the result is a second app wearing the vault's CSS. Two consequences follow:

  • An order line item should be able to resolve to a vault item — the same product identity the vault already uses for a sealed box or a card.
  • A delivered order should be able to create or increment vault inventory, with the order as its provenance and its price as the cost basis.
Depends on the vault

How tightly line items bind to vault items depends on whether the vault has a product catalog with stable identity, or whether items are free-text. Both are workable — see §09. Ship the loose version first; tighten later.

03

Scope

In scope

  • Connecting one or more email accounts and scanning them for order mail
  • User-authored rules that decide which mail counts and what it means
  • Extracting order number, date, total, line items, status and tracking
  • Manual entry of product release dates
  • A cash-due timeline and supporting order views
  • Hand-editing and hand-creating orders, with edits protected from being overwritten

Out of scope for v1

  • Scraping retailer websites or using retailer APIs — email only
  • Automatic background scanning on a schedule (manual trigger in v1; see §12)
  • Payment or card integration of any kind
  • Price/market-value tracking — the vault's existing concern, not this feature's
  • Partial shipments splitting one order across dates

Non-goals

This is not a general email client, and not a purchase-approval workflow. It reads mail and never sends any.

05

Rules engine

This is the feature the user asked for by name. It is about 100 lines of logic with no dependencies and should be ported precisely — the semantics are what make it predictable.

R-1

Every non-empty condition on a rule must pass. Conditions left blank are ignored.

R-2

Within a single condition, comma-separated terms are OR'd. shipped, on its way matches either.

R-3

subject_excludes inverts: the rule fails if any of its terms appear.

R-4

Matching is case-insensitive substring by default. When use_regex is set, every term in every condition is treated as a pattern instead. An invalid pattern fails closed — it does not throw.

R-5

Sender matching runs against display name and address concatenated, so both Pokemon Center and pokemoncenter.com work as terms.

R-6

Rules are evaluated in ascending priority, then ascending id. First match wins and evaluation stops.

R-7

A rule with zero conditions matches nothing. It must never match everything.

R-8

The union of every enabled rule's from_contains terms drives the IMAP search, so scanning only downloads mail that could possibly match.

Rules that must ship by default

Order matters — cancellations and shipping notices must be checked before the generic order rule, or a "your order has shipped" email gets filed as a new order.

PriNameConditionsKind / timing
5Pokémon Center cancellationsfrom pokemoncenter.com · subject cancel, canceled, cancelled, refundcancellation
10Pokémon Center pre-ordersfrom pokemoncenter.com · subject pre-order, preorder, pre orderpreorder / at_ship
15Pokémon Center shippingfrom pokemoncenter.com · subject shipped, on its way, shipmentshipment / at_ship
20Pokémon Center ordersfrom pokemoncenter.com · subject order, thanks for your order · NOT cancel, shipped, delivered, refundorder / at_order
30Target Pokémon ordersfrom target.com, oes.target.com · subject order · NOT cancel, delivered, return · body pokemon, pokémonauto / at_ship

That last rule demonstrates the pattern for any store that sells more than trading cards: the body condition is what keeps a Target order for bath towels out of the vault.

R-9

Rule tester. The user can paste an email — or select one already downloaded — and see which rule wins, which individual conditions passed or failed, and what would be extracted. Non-negotiable: rules are unpredictable without it.

R-10

Re-apply without re-scanning. Changing a rule must be able to rebuild orders from mail already stored, with no network round-trip. Scans are slow; iterating on rules must not be.

06

Email parsing

Retailers change templates constantly. The design principle is that parsing failures surface rather than get guessed at.

R-11

HTML bodies are flattened to text before parsing. Table cells become spaced text, block elements become newlines, script and style are dropped. Prefer whichever of the plain and HTML parts carries more content — marketing mail often ships a near-empty plain part.

R-12

Total extraction is priority-ordered. Look for labelled totals first (order total, grand total, total charged), then bare total, then a trailing currency amount. Matching the first dollar figure in the email returns the subtotal and is wrong.

R-13

Order number is searched in the subject before the body. Reject anything shorter than six characters — short numeric matches are dates and quantities.

R-14

Line items are attempted with several layouts in turn: name/qty/price on one line, then the flattened-table case where each sits on its own line. Lines whose text contains subtotal, shipping, tax, discount and similar must never be treated as products.

R-15

Return zero line items rather than fabricated ones. An order with a correct total and no items is useful; an order with an item called "Estimated Tax" is not.

R-16

Any matched email that yields no order number, no total, or line items summing to more than the total goes to a review queue with a plain-language note. It does not fail silently and it does not throw.

Upsert behaviour

Keyed on (retailer, order_no). A shipping notice for an existing order updates it; it never creates a duplicate.

kind = cancellation  → status = cancelled, charged = false
kind = delivery      → status = delivered
kind = shipment      → status = shipped, tracking = extracted
                       if charge_timing ≠ at_order: charged = true,
                       charge_date = email date
kind = order         → fill total and items only if currently empty
kind = preorder      → status = preorder if currently open

// In every branch, skip any field listed in order.locked
R-17

Hand edits win permanently. Editing any order field adds that field name to locked. No scan, upsert or rebuild may ever overwrite a locked field. Orders with notes, and orders the user created by hand, survive a rebuild untouched.

07

Money model

This is the substance of the feature. Everything else is plumbing that feeds it.

The distinction that matters

Pokémon Center authorizes your card when you place a pre-order but does not charge until the item ships. Most retailers behave similarly for pre-orders. So an order occupies one of two states that a naive "total spent" number conflates:

Charged — the money has left. It belongs in spend history and nowhere else.

Committed but not charged — the money is owed. It belongs on the cash timeline, on the date it will actually be taken.

R-18

charge_timing is resolved once, at order creation, from the matching rule. When the rule says auto: a pre-order resolves to at_ship, anything else to at_order.

R-19

A new order is marked charged immediately if timing is at_order, or if it arrived already shipped or delivered. Cancelled orders are never charged.

Allocation algorithm

Runs over every order that is not charged and has status preorder or open. It allocates money to dates, and it allocates per line item where possible — an order containing two products releasing in different months must split across both dates, not pile onto one.

for order in uncharged_open_orders:

  // Explicit beats inferred, in this order
  if order.charge_date:    allocate(order.charge_date, order.total)
  elif order.release_date: allocate(order.release_date, order.total)
  elif timing == at_order: allocate(order.order_date, order.total)

  else:
    matched = 0
    for item in order.items:
      release = best_release_match(item.name, order.retailer)
      if release:
        allocate(release.release_date, item.line_total)
        matched += item.line_total

    leftover = order.total - matched   // tax, shipping, unmatched items

    if matched > 0 and leftover > 0:
      allocate(latest_matched_date, leftover)
    elif matched == 0:
      fallback = best_release_match(all_item_names, order.retailer)
      if fallback: allocate(fallback.release_date, order.total)
      else:        allocate(UNSCHEDULED, order.total)
R-20

best_release_match returns the release whose longest matching term appears in the text — most specific wins. A release with a retailer set only matches orders from that retailer.

R-21

Tax and shipping ride along with the latest matched item's date, since that is when the order actually ships and charges.

R-22

Money that cannot be dated goes to an explicit unscheduled bucket that is visible in the UI and links to release-date entry. It must never be silently dropped or silently folded into a real date.

R-23

Allocation is computed on read, never stored. Changing a release date must move the money immediately, with no rescan and no rebuild.

09

Open decisions

These cannot be settled without reading the vault's code. Each needs an answer before implementation, and each has a safe default.

D-1 · Item identity

Does the vault have a product catalog with stable identity? If yes, order_item gets a nullable foreign key to it, and release dates hang off catalog entries. Default if unclear: keep item names as free text with match_text bridging, and add the key later — nothing in the money model depends on it.

D-2 · Do delivered orders create inventory?

The §02 vision says yes. It may not be safe to do automatically if the vault's inventory has required fields an order can't supply. Default: offer it as an explicit "add to vault" action on a delivered order rather than an automatic side effect.

D-3 · Where does IMAP run?

If the vault is a pure browser app with no backend, IMAP is not reachable from the client and this needs a server component or a local helper process. If the vault already has a backend or is a desktop app, it runs there. This is the decision most likely to change the shape of the work — settle it first.

D-4 · Secret storage

App passwords need encrypting at rest. If the vault already has a secrets mechanism or an OS keychain integration, use it. Default: encrypt with a key in a separate local file, and be explicit in the UI that this is local obfuscation, not protection against someone with the machine.

D-5 · Migrating vs starting fresh

See §10. If the standalone app has not been run against real mail yet, starting fresh is strictly simpler and loses nothing.

10

Migration

The standalone app stores everything in one SQLite file at data/poketrack.db. Tables map to §04 one-to-one, so migration is a read-and-insert, not a transform.

R-25

If migration is needed: import rules, releases, orders, items and emails in that order. Preserve locked exactly — it encodes user corrections that would otherwise be silently reverted on first rebuild.

Mail accounts should not be migrated. The stored secret is encrypted with a key tied to that install; re-entering app passwords is quicker and cleaner than porting the key material.

11

Acceptance tests

These are lifted from the reference implementation's passing suite, with real numbers. An implementation that satisfies them behaves correctly.

Rules

  • "Your pre-order is confirmed" from orders@pokemoncenter.com → matches the pre-order rule, not the order rule
  • "Your order has shipped" from shipping@pokemoncenter.com → matches the shipping rule
  • "New arrivals at Pokémon Center" from news@pokemoncenter.com → matches nothing
  • A Target order for bath towels with no Pokémon content → matches nothing

Parsing

  • An order email with subtotal 124.97, tax 10.31, order total 135.28 → extracted total is 135.28, never 124.97
  • Same email → exactly 2 line items; neither is named "Subtotal", "Estimated Tax" or "Shipping"
  • An item at qty 2 × $49.99 → line total 99.98
  • A shipping notice for an existing order → updates it to shipped with tracking; total order count does not change

Money

Worked example. Two uncharged pre-orders and one Target order, against releases mega evolution → 2026-09-26 and destined rivals → 2026-10-17:

AssertionExpected
Owed on 2026-09-26 (two stores, one release)346.84
Owed on 2026-10-17175.30
Unscheduled0.00
Total still owed522.14
Total already charged309.85

Note that 346.84 spans two retailers releasing the same product on the same day — the timeline is organised by date, not by order.

  • Moving destined rivals to 2026-11-07 → the 10-17 bucket disappears and an 11-07 bucket appears, with no rescan and no rebuild
  • A cancelled order contributes zero to owed and to charged

Durability

  • Hand-edit an order's total to 999.00, then rebuild from stored mail → total is still 999.00 and its notes survive
  • Rebuild twice → order count is unchanged both times
12

Phasing

Each phase is independently useful, which matters — phase 1 alone answers the original question.

P-1

Manual core. Orders, line items, releases, the allocation algorithm, the cash timeline and hand entry. No email at all. This delivers the actual value and de-risks everything downstream, because the money model is the part worth getting right.

P-2

Rules and parsing, offline. Rules engine, parser and the rule tester, run against pasted email text. Testable without touching IMAP.

P-3

Mail ingestion. Accounts, IMAP scanning, the review queue, re-apply. Resolves D-3 and D-4.

P-4

Vault integration. Item identity binding and delivered-order-to-inventory per D-1 and D-2. The part that makes it one app rather than two.

P-5

Automation. Scheduled scanning and a heads-up when a charge date is approaching.

Reference implementation: PokeTrack (Python, standard library only) — data model, algorithms and the full passing test suite. Ported logic lives in rules.py, parser.py and money.py; the UI layer is not worth carrying over.
